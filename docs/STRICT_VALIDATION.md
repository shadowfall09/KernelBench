# 严格数值契约与证据等级

这是23项设计的第一批实现，推进R-04/05/06/07/09，并交付R-17聚合消融、R-22证据收据的代码。它是现有标准/隐藏验证之后的附加门：已有正确性、计时与证据门继续执行。

## 使用

```bash
# 原有协议仍为默认；显式开启附加契约。
python scripts/run_batch.py --config configs/a6000-feedback.toml \
  --strict-validation --level 1 --start 1 --end 3

# L0自动要求严格校验；原有GPU后端和Harbor使用同一配置。
python scripts/run_batch.py --config configs/a6000-feedback.toml \
  --evidence-level L0 --level 1 --start 19 --end 27 --dry-run
```

TOML中使用`[run] strict_validation = true`、`evidence_level = "L0"`。`current`是既有等级，L0/L1/L2要求在下表列出。不同配置分别比较，配置、契约文件和评测模块均进入恢复指纹。旧结果需要重评；不能只给旧JSON加等级字段。

当前适配17道L1：1–3、19–27、47–49、51–52。参考源码SHA-256、输入族、状态语义和各dtype阈值保存在随包分发的[契约清单](../kb_workflows/numerics/verification_contracts.json)。未适配题、参考漂移、无法构造oracle或缺失必要收据，在严格模式下不给通过资格。CLI会在创建运行目录或调用模型前拒绝含未适配题的严格任务；`--dry-run`显示覆盖范围。直接提交到worker的未适配任务也不会获得严格资格。

## FP64与输入范围

另可独立使用`--numerical-validation`检查原L1全部100题的实际标准/隐藏输入：采用CPU独立算式和显式主机内存包络，不改变原尺寸；参考自身不合格或缺证据时拒绝通过。这与此页17题的小实例附加契约是不同入口，仍不授予全套L0，见[原生输入数值复核](NUMERICAL_VALIDATION.md)。

参考和候选分别在独立输入和模型副本上运行；可信参考的副本使用float64（比较工具也支持complex128）。转换保留整数、bool和嵌套结构。参考自己也必须满足FP64契约，否则该数值检查不成立，不用放宽阈值让候选通过。

每个浮点输出叶子同时要求：

```
RMS(candidate - oracle) <= norm_atol + norm_rtol * RMS(oracle)
每个元素的误差 <= element_atol + element_rtol * abs(oracle_element)
                  + element_scale_rtol * RMS(oracle)
```

最后的全局量级项允许合法fp32求和在接近零的元素上产生小误差；它也是显式契约参数。所有元素必须满足元素门。结构、shape、输出dtype、离散值和非有限值位置仍须符合契约。收据逐叶保存误差、限值、失败元素数和参考是否合格。

阈值目前是明确公布的初始契约，经过小规模真实CPU参考验证，并不是完成GPU误差分布校准的结论。附加实例使用小规模合法尺寸，避免构造原题巨大的FP64副本；**原尺寸计时输入仍使用既有比较器**。因此不能把L0解释成所有原始尺寸都已被FP64验证，也不能把这些实例的成本或耗时当作正式性能分数。

公开开发阶段只用第一组尺寸；隐藏阶段另外增加第二组奇数尺寸与非连续stride。矩阵相乘的维度联动，reduction保留合法维数；不缩放索引、mask或概率输入。输入族包括有符号数、近常数、宽动态范围、边界元素决定结果，以及GELU的±2.699辨别值。未核对的任务不会获得泛化扰动。

参考信号诊断记录有限值覆盖、最大值、RMS、超过绝对容差比例与常数标记。常数输出本身不判语义错误；要求至少一组合法实例提供有效信号。当前尚未自动修复所有原尺寸退化输入，也没有重建相应性能基线。

## 状态、缓存与进程设置

同一输入对象先运行，再原地修改后重跑；只有参考响应发生变化时，候选保持原输出才构成缓存问题。状态契约检查连续的train/eval切换、注册buffer和参数更新，支持声明式重命名、切片、转置及不复制存储的reshape。映射必须保留数值、元数据和共享关系；未注册参考Tensor状态、非线性重参数化或无法隔离的快照不能静默通过。完整接口见[状态审计](STATE_VALIDATION.md)。

`--state-validation`（TOML：`state_validation = true`）可单独开启实际输入上的状态审计，不要求该题已有17题中的FP64附加契约。它在独立复核worker中覆盖每个实际原生标准/隐藏实例，绑定同一源码、配置、种子、设备与请求预算，评分和恢复重新核对收据。该开关不构成完整L0资格，也不将诊断时间用于性能分数。

候选首次原生评测、再次导入和附加调用都被进程设置审计覆盖。审计恢复后端精度/确定性设置、默认dtype、CPU线程数与环境变量，并把变更记录为失败。收据只含环境变量名称，不包含值。恢复和进程包装不是OS安全隔离，也不保证抓到候选在调用中修改后又恢复的全部行为。

## 等级与评分

| 等级 | 累计必要证据 | 当前状态 |
| --- | --- | --- |
| current | 本阶段原生正确性 | 默认协议；不提供完整执行合法性证明 |
| L0 | current + FP64契约、参考信号、合法输入族、输入敏感性、环境完整性、模式/状态 | 已有逐项软件路径；需当前范围实际证据，CPU回归不提供设备资格 |
| L1 | L0 + 交替计时、噪声底、内核来源、设备校准、边界证书、启动收益归因 | 缺少实际证据时拒绝该等级和相应评分资格 |
| L2 | L1 + 硬件计数器、内存工具、重复一致性、算法证书、独占设备观察 | CUDA评分组装重放各阶段原始工件；Neuron及未校准非kernel传输不具备该路径 |

每项记录`passed`、`failed`、`not_measured`或有理由的`not_applicable`，未知测量值为null。receipt同时记录请求等级、达到等级、缺项、standard/hidden范围；评分器重新根据逐项证据计算资格，不只信汇总布尔值。安全隔离认证仍为false。可选[受限验证器](ISOLATION_REGRADE.md)记录Docker配置、Linux观察和清理，并进入评分/恢复，但不替代来源、计数器或真实隔离验收。

L1在分析阶段汇总外部测量证据：先从当前配对结果重算原始样本、实际来源和匹配的持续采集模式，再逐次核对设备校准以及输入、精度、参考源码绑定的审查证书。噪声检查表示已估计参考/控制噪声，收益仍须另行超过该噪声底。每个独立repeat都核对实际参考/候选/控制设备窗口；仅由启动成本解释的收益标为`launch_only`并置零，复测分类混合或活动缺失也不给L1资格，见[实际配对归因](HEADROOM_SCORING.md#实际配对归因与启动收益)。五项测量检查合并后才判定标准、隐藏及全部冻结复测资格。原始`eval_results*.json`保持worker收据，`paper_analysis.json`和`eval_results_scored.json`另存合并判定与来源哈希。CUDA L2继续重放各阶段规范计数工件、逐内核资源模型、独占驱动观察和四工具/重复收据；缺失、改变或缓存的passed标签不能代替材料，见[L2支持范围](WORK_COUNTERS.md#cuda-l2评分组装)。

原始正确性和计分资格有区别：原生输出正确但缺L1工具时可以保留诊断结果，评分资格则被拒绝。真正执行失败或严格必要项失败时，正确性也不能计作通过。`--no-hidden-tests`仍不代表已通过隐藏验证；报告明确记录是否启用。

可选内存工具与重复一致性使用独立诊断worker，默认关闭。审核后的原子操作波动策略不放宽原生或FP64精度门，见[工具说明](TOOL_CHECKS.md)。

## 聚合消融

`paper_analysis.json`新增`aggregation_sensitivity`，对同一批声明题目×样本槽位分别计算mean、median、best-of-N，保留失败/缺失零分和原资源收据。它显示同一批产物因聚合规则造成的变化，不增加模型调用、不修改正式mean评分，也不将未知预算认证为同等成本。跨生成策略的研究实验仍需真实模型数据。

## 验证范围

回归包含17道真实PyTorch参考的FP64/隐藏形状运行，以及BF16冒充FP32、GELU近似、单元素错误、结构/dtype/非有限值、输入身份缓存、参数缓存、BN计数器、环境恢复、秘密值不序列化、缺工具收据与聚合分母等反例。实际CUDA、所有题目适配、GPU阈值校准和生产模型实验分别验收，不以CPU测试替代。

## L1/L2的实际执行来源

CUDA L1/L2现在为候选、配对参考/控制和基线启用同一种持续CUPTI模式；实际计时保留原始model对象。`kernel_track`选择custom或library，`origin_minimum_custom_fraction`默认0.95；政策绑定配置、恢复和实验分组。`kernel_origin`只从实际计分进程的源码/产物/launch与完整调用收据推导，评分离线重算，独立重放或模拟证据不能代替。采集缺失或未知来源不给资格，也不修改数值正确性。详见[实际来源门](KERNEL_ORIGIN.md#实际计分模式与来源门)。其他L1/L2门及本页严格契约覆盖要求仍须满足；这不是全等级通过、硬件实验完成或安全认证。
